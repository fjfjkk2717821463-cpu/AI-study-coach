# 发布流程

这份文档说明「改代码 → 出新版本 → 用户收到更新提示」的完整流程。

目标只有一个：**任何一个版本都能立刻回答三个问题——版本号是多少、这一版改了什么、代码停在哪一个提交上。**

## 一、版本号只有一个来源

版本号的唯一来源是 `app.py` 顶部的 `VERSION`。

下面四处必须始终一致：

| 位置 | 说明 |
| --- | --- |
| `app.py` 的 `VERSION` | 界面右下角显示、`/api/version` 返回的版本 |
| Git 标签 | `v` + 版本号，例如 `v2.0.0` |
| GitHub Release | 标题以 `v` + 版本号开头 |
| `CHANGELOG.md` | 有一个 `## [2.0.0] - 日期` 这样的小节 |

原因：App 每次启动都会去读 GitHub 上**最新的 Release**，把标签名去掉 `v` 之后和自己的 `VERSION` 比较，不一致就提示「有新版本」。

> 所以「改了代码但没发 Release」等于用户永远收不到更新提示；
> 而「发了 Release 但忘了改 `VERSION`」会让用户被反复提醒升级到同一个版本。

## 二、该升到哪个版本号

版本号遵循[语义化版本](https://semver.org/lang/zh-CN/)：`主版本.次版本.修订号`。

| 改动性质 | 怎么升 | 例子 |
| --- | --- | --- |
| 不兼容的改动：数据格式、目录结构、使用方式变了 | 主版本 +1，次版本与修订号归零 | 用户数据目录改名、总结文件格式变化 |
| 向下兼容地新增功能 | 次版本 +1，修订号归零 | 新增「默写模式」 |
| 只修 bug、改文案、调样式 | 修订号 +1 | 修复 PDF 页眉被当章节 |

## 三、日常改动怎么提交

1. 一个功能一个提交，提交信息写清楚「做了什么」，例如 `feat: 新增默写模式`。
   常用的前缀：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`chore`（杂事）、`security`（安全）。
2. 提交前会自动跑密钥扫描（已启用 `.githooks` 钩子时）；发现疑似密钥会直接拦截。
3. 推送前跑一遍测试：

   ```bash
   .venv/bin/python -m unittest discover -s tests
   ```

## 四、发一个正式版本

```bash
# 0. 先确认没有未提交的改动，且测试通过
git switch main
git status
.venv/bin/python -m unittest discover -s tests

# 1. 只体检：检查版本号、标签、更新日志是否一致
python tools/release.py --check

# 2. 改版本号 + 生成更新日志小节
python tools/release.py 2.1.0 --title "教师端增强"

# 3. 打开 CHANGELOG.md，把 v2.1.0 这一节写完整
#    分类用「新增 / 变更 / 修复 / 安全」，每条写清楚对用户意味着什么

# 4. 提交 + 打标签 + 推送 + 建 GitHub Release
python tools/release.py --publish
```

第 4 步会自动完成：跑测试 → 扫密钥 → 提交 `chore(release): v2.1.0` → 打标签 `v2.1.0` → 推送到 GitHub → 用更新日志里这一节的正文创建 Release。

只想先提交和打标签、稍后再推送，用 `--no-push`；只想看看会执行哪些命令，用 `--dry-run`。

发布之后可以核对：

```bash
gh release view v2.1.0          # 看 Release 是否创建成功
curl -s http://127.0.0.1:8000/api/version   # 看 App 报的版本号
```

## 五、发布检查清单

- [ ] 测试全绿（`unittest discover -s tests`）
- [ ] 密钥扫描无高危项（`tools/secret_scan.py --history`）
- [ ] `CHANGELOG.md` 里这一版写清楚了新增 / 变更 / 修复 / 安全
- [ ] `app.py` 的 `VERSION`、标签名、Release 标题三者一致
- [ ] 应用内更新提示验证过：旧版本启动后能看到「有新版本可用」
- [ ] 需要分发安装包时，把 `.zip` 作为 **Release 附件**上传
      （不要提交进仓库：仓库里的 `打包产物/`、`打包产物-学习版/` 已被忽略）

## 六、必须记住的几条规矩

1. **不要重写已发布的标签。** 标签一旦公开，别人可能已经克隆或下载。
   发错了就发一个修订号（`2.0.1`），而不是 `git tag -f`。
2. **不要把密钥和私密材料提交进仓库。** `.env`、`model_config.json`、
   `大赛申报/`、`进校材料/`、`交付给老师/` 都已在 `.gitignore` 里；
   新增目录时先确认是否需要忽略。
3. **发布前先扫一遍全量历史。** 仓库已经开源，历史里的任何东西都是公开的：

   ```bash
   python tools/secret_scan.py --all --history
   ```

4. **Release 说明直接来自 `CHANGELOG.md`。** 先把更新日志写好，
   再执行 `--publish`，这样网页上的说明和仓库里的记录不会各说各话。

## 七、自动测试

[.github/workflows/ci.yml](../.github/workflows/ci.yml) 已经在运行：

- **触发时机**：推送到 `main`、以及每一个 PR。
- **做什么**：在 Ubuntu + Python 3.12 上安装 `requirements-cloud.txt`，
  跑全部单元测试，再跑一次密钥扫描。任何一步失败，提交记录旁会出现红叉。
- **在哪里看**：仓库的 Actions 标签页，或 `gh run list` / `gh run watch`。

查看最近几次运行：

```bash
gh run list --limit 5
gh run watch          # 实时跟进正在跑的那一次
```

> **推送工作流文件需要额外权限。** GitHub 规定：令牌必须带 `workflow` 权限，
> 否则 `git push` 会被拒绝（提示 `refusing to allow an OAuth App to create or update workflow`）。
> 本项目当前令牌已补齐该权限；换新令牌时先执行一次 `gh auth refresh -s workflow`。
